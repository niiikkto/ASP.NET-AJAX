# Конспект: Фоновые очереди (Channels) и Тонкий HTTP-клиент в .NET

Документ охватывает два архитектурных паттерна в C# / .NET:
1. Организация асинхронной фоновой очереди задач с помощью `System.Threading.Channels` и `BackgroundService`.
2. Реализация типизированного «тонкого» HTTP-клиента с паттерном `Result` (без выброса исключений на ожидаемые ошибки).

---

## Часть 1. Асинхронные фоновые очереди (`System.Threading.Channels`)

> *Примечание: В заголовке исходного файла указано «ADO.NET», однако технически код демонстрирует работу с пространством имен `System.Threading.Channels` и фоновыми службами `Microsoft.Extensions.Hosting`.*

### 1.1. Назначение
Паттерн **Producer-Consumer (Производитель-Потребитель)** позволяет разгрузить основной поток обработки веб-запросов:
* **Производитель (Producer):** HTTP-контроллер или эндпоинт быстро помещает задачу в очередь и сразу возвращает ответ клиенту.
* **Потребитель (Consumer):** Фоновая служба (`BackgroundService`) последовательно или параллельно извлекает задачи из очереди и выполняет их.

### 1.2. Основные компоненты

#### 1. Интерфейс очереди (`IBackgroundTaskQueue`)
Определяет контракт для добавления и извлечения делегатов (асинхронных задач, принимающих `CancellationToken` и возвращающих `ValueTask`).
* `QueueAsync(...)` — постановка задачи в очередь.
* `DequeueAsync(...)` — асинхронное извлечение задачи.

#### 2. Реализация на базе `Channel<T>` (`BackgroundTaskQueue`)
Используется ограниченный канал (`Channel.CreateBounded<T>`), чтобы избежать переполнения памяти (OutOfMemory) при всплеске запросов.
* **Настройки `BoundedChannelOptions`:**
  * `FullMode = BoundedChannelFullMode.Wait` — если очередь заполнена (`capacity`), производитель асинхронно ждет освобождения места (создает *backpressure* / противодавление).
  * `SingleReader = true` — оптимизация под одного читателя (одну фоновую службу).
  * `SingleWriter = false` — разрешает конкурентную запись из множества потоков (веб-запросов).
  * `AllowSynchronousContinuations = false` — предотвращает выполнение продолжений потребителя в потоке производителя.

#### 3. Фоновый обработчик (`QueueConsumerService : BackgroundService`)
* Наследуется от `BackgroundService` и переопределяет метод `ExecuteAsync(CancellationToken stoppingToken)`.
* Работает в бесконечном цикле `while (!stoppingToken.IsCancellationRequested)`.
* **Обработка ошибок и остановки:**
  * Перехватывает `OperationCanceledException` при остановке приложения для корректного выхода из цикла.
  * Перехватывает общие `Exception`, логирует их, но **не дает службе упасть**, чтобы обработка следующих задач продолжилась.

#### 4. Регистрация в DI и запуск (`Program`)
* Очередь регистрируется как `Singleton` (`AddSingleton<IBackgroundTaskQueue>`), так как она должна быть общей для всех запросов и фоновой службы.
* Потребитель регистрируется через `AddHostedService<QueueConsumerService>()`.

## Часть 2. Тонкий HTTP-клиент (`ThinClient.Http`)

### 2.1. Архитектурная идея
Вместо того чтобы разбрасывать работу с `HttpClient`, сериализацию JSON и `try-catch` блоки по всему приложению, создается многоуровневая обертка:
1. **Уровень результата (`ApiResult<T>`):** Реализация паттерна *Result Object*. Ошибки сети, таймауты и HTTP-статусы (400, 404, 500) возвращаются как значения, а не выбрасываются как исключения.
2. **Транспортный уровень (`HttpTransport`):** Инкапсулирует работу с `HttpClient`, заголовками, авторизацией (Bearer-токен), сериализацией и обработкой исключений.
3. **Уровень контракта (`UsersApi`):** «Тонкий» класс, описывающий конкретные эндпоинты API и DTO-модели (рекорды `User`, `CreateUserRequest` и т.д.).

### 2.2. Ключевые элементы реализации

#### 1. Унифицированный ответ (`ApiResult<T>` и `ApiError`)
* `ApiResult<T>` (реализован как `readonly struct` для минимизации аллокаций памяти):
  * `IsSuccess` — флаг успеха.
  * `Data` — десериализованные данные (если успешно).
  * `Error` — объект ошибки `ApiError` (если неуспешно).
  * `StatusCode` — HTTP-код ответа.
* Классификация ошибок (`ApiErrorKind`):
  * `Network` — проблемы с сетью (`HttpRequestException`).
  * `Timeout` — истекло время ожидания ответа.
  * `Http` — сервер вернул код ошибки (не `2xx`).
  * `Parse` — сервер вернул невалидный JSON (`JsonException`).
  * `Canceled` — запрос был явно отменен пользователем/кодом через `CancellationToken`.

#### 2. Транспортный слой (`HttpTransport`)
* **Формирование запроса:** Автоматически добавляет `Accept: application/json`, заголовок `Authorization: Bearer <token>` (через делегат `Func<string?>`) и сериализует тело запроса в `camelCase`.
* **Различение отмены и таймаута:**
  * `HttpClient` выбрасывает `TaskCanceledException` в обоих случаях.
  * Конструкция `catch (TaskCanceledException) when (ct.IsCancellationRequested)` позволяет точно определить, что запрос отменил сам вызывающий код, а обычный `catch (TaskCanceledException)` трактуется как таймаут `HttpClient`.
* **Парсинг структурированных ошибок:** При получении неуспешного HTTP-статуса пытается прочитать из тела ответа поля `code`, `message` и `details` через `JsonDocument`.

#### 3. Тонкий клиент API (`UsersApi`)
* Не содержит логики обработки ошибок или HTTP-заголовков — только маппинг методов C# на URL-пути и HTTP-методы (`GetAsync`, `PostAsync`, `PatchAsync`, `DeleteAsync`).
* Использует `Uri.EscapeDataString` для безопасной подстановки параметров в URL.

#### 4. Важные практики в `Program`
* **Переиспользование `HttpClient`:** Экземпляр `SharedClient` создан как `static readonly`, чтобы избежать исчерпания сокетов (*Socket Exhaustion*).
* **Декларативная обработка ошибок:** Вызывающий код проверяет `result.IsSuccess` и обрабатывает конкретные сценарии (например, `400 BadRequest` для валидации или `404 NotFound`) без громоздких блоков `try-catch`.
